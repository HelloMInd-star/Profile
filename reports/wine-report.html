1执行摘要

先给结论，再给证据。

一句话定位

Y.Mine 不应被理解成「又一个鸡尾酒配方 App」，而应是 以人格向量为统一中间层的多感官体验编排系统——同一组输入，确定性地产出酒、色、香、味、音、光六个通道的参数。

它的真正资产不是"人格调酒"这个概念，而是三层可验证的硬设计：① OCEAN→六维→八维风味的加权矩阵映射（数学可解释、纯函数、有测试）；② 每款酒自带八维风味画像，构成匹配的数据基础；③ 六通道共享同一数据契约，而非各自独立的随机效果。

三个最有价值的判断

有证据

不是配方库，是体验编排层

Cocktail Flow、Difford's 解决"找配方"，Foodpairing 解决"风味计算"。Y.Mine 解决的是让六个感官通道共享同一套可解释参数——这是不同层次的问题。

差异化

单点已红海，闭环仍空白

人格输入（MBTI 歌单）、单通道输出（配方推荐）都已成熟；但"输入—向量—多输出—制作—反馈"的完整闭环，公开资料中尚未见到成熟产品。

风险

最大风险是从未进过真实吧台

主流程存在已知集成测试失败（MoodDial intensity 异常），且从未在真实酒吧验证过制作闭环。酒吧买的是运营指标，不是人格报告。

2核心抽象：六维向量作为统一数据契约

这是整个系统真正的地基，也是"人格调酒"这个漂亮名字遮蔽掉的最值钱部分。

Y.Mine 的所有感官模块共享同一个抽象：把人的状态表示为一组可计算的向量，再让不同通道消费这组向量。

六维人格向量

TOL 容错SPD 速度INF 信息 ENT 热情LEAD 主导VIS 直觉

范围 [-1, 1]，50 分为中性零点。纯函数派生，无副作用。

OCEAN → 六维：映射设计有明确的产品思考

OCEAN 维度→ 六维权重设计意图
Openness 开放性VIS 直觉1.0开放性 → 直觉与灵感
Conscientiousness 尽责性INF 信息1.0尽责性 → 信息依赖与谋略

这个设计最精妙的一处：源码注释写着「测评回答你是怎样的人，牌类回答你怎么决策」——SPD（决策速度）被刻意留空，只由对局行为贡献。这说明向量不是拍脑袋定的维度清单，而是按数据来源做了语义分工。

向量是跨项目复用的

同一套六维向量，在金融孪生平台里驱动风险预算与投资人匹配，在调酒系统里驱动风味、颜色、气味、音乐。这不是两个独立项目，而是一个抽象在两种场景下的复用——这是整个作品矩阵（12 个应用）真正的统一内核。

3人格 → 感官：6×8 风味加权矩阵

这是全项目技术含量最高、也最能体现"产品经理 + 工程"复合能力的一块。

flavorFromVector.ts 定义了一个 6×8 的加权矩阵，把六维人格向量映射为八维风味偏好：

风味维度TOLSPDINFENTLEADVIS语义解释
sweet 甜0.1000.400.2热情 + 直觉 → 偏好甜
sour 酸00.30.10.100决策快 → 偏好清爽
bitter 苦00.10.4−0.20.20信息驱动 → 苦；热情抑制苦

矩阵约束：每行权重绝对值之和 ≤ 1，保证输出落在 [−1, 1]；负权重表示该维度压制该风味。全零向量输出中性 0.5。

为什么这个矩阵值钱：它不是"ENTJ → 莫吉托"这种拍脑袋的查表，而是一个可微、可测、可解释的线性映射。你能说出「这杯酒偏苦，是因为你 INF 得分高、而 ENT 压低了它」——每一步都能解释。这正是"可控、可审计的体验编排"与"装饰性人格标签"的分界线。

另外三个派生引擎

colorFromVector

六维 → HSL 色彩（hue / saturation / lightness）。替代了旧版"10 种原型 10 个固定色"的硬编码方案，改为连续派生。

scentFromVector

对每个维度按正负取出对应气味 note，输出主调 + 副调两个音符。向量空间中维护完整 note 列表供 UI 渲染气味谱。

musicEngine（23.8KB）

Web Audio API 实时生成，配 musicProfileEngine（18.7KB）+ audioAnalyzer 频谱分析。是六通道里技术最重的一个。

4推荐引擎：八维风味画像 + 余弦相似度

矩阵算出"你偏好什么风味"之后，还需要回答"哪款酒匹配"——这一步同样是可解释的。

每款酒自带八维风味画像

关键在于：配方库里每款酒都预标注了八维 flavorProfile（0-10 分），与人格侧输出的八维偏好维度对齐。这是匹配能成立的数据基础。

// gin.ts · 干马天尼（节选）
{
  id: 'gin-dry-martini', name: '干马天尼', nameEn: 'Dry Martini',
  tagline: '极简配方中蕴藏着无限微妙的平衡。',
  story: '它是鸡尾酒界的"白衬衫"——金酒、味美思、橄榄或柠檬皮…',
  baseSpirit: 'gin', abv: 28, glass: 'martini',
  flavorProfile: { sweet:0, sour:1, bitter:3, strong:7,
                      smoky:0, fruity:0, herbal:6, creamy:0 },   // ← 八维画像
  ingredients: [...], steps: [...], moods: ['elegant', 'calm']
}

数据结构的完整度

  • 双语名称 + tagline + 富文本故事（story）
  • 基酒分类、ABV 酒精度、杯型、装饰
  • 八维风味画像（与人格侧维度对齐）
  • 配料（含用量与备注）、分步制作流程
  • moods 情绪标签（elegant / calm 等）

这不是"配方列表"，而是结构化知识库——故事字段直接支撑了后续的叙事生成。

三种推荐路径

  • recommendCocktails — 风味距离匹配，输出 0-100 匹配分
  • recommendByArchetype — 按人格原型推荐
  • recommendByVector — 直接由向量驱动

computeFlavorDistance 计算相似度，generateMatchReasons / generateArchetypeReasons 生成可读的推荐理由——不只给结果，还给解释。

推荐理由生成器是关键设计。多数推荐系统只输出"为你推荐：莫吉托"。Y.Mine 会输出为什么——「你的 ENT 偏高 → 偏好果香与甜感 → 这款酒的 fruity 维度得分为 X」。这把"黑箱推荐"变成了可解释的对话，也直接创造了分享与社交传播的理由。

5多感官编排：六通道共享同一组参数

这是与所有配方类 App 拉开代差的地方。

🍸 酒

八维风味匹配 → 具体配方 + ABV + 杯型 + 装饰 + 分步制作

🎨 色

colorFromVector → HSL 主色/辅色，驱动 FlavorSpectrum 色阶渐变

👃 香

scentFromVector → 主调 + 副调气味 note，含完整气味谱

👅 味

八维风味权重 → 味觉画像，可直接驱动色阶与推荐

🎵 音

musicEngine（23.8KB）Web Audio 实时生成 + 频谱分析

💡 光

lightEngine + scentEngine 联动，氛围参数化

核心差异不是"通道多"，而是"同一个输入"。传统方案里，酒单、灯光、歌单由三个人分别决定，彼此无关。Y.Mine 里它们由同一组向量的同一次计算派生——同一输入 + 同一规则版本 = 可复现的输出组合。这带来三个工程价值：
  • 版本管理：映射规则可迭代、可回滚、可 A/B
  • 设备接口：色/音/光参数可标准化输出给灯具、音响、互动屏
  • 线下复现：同一人格在不同门店应得到一致体验——这是连锁部署的前提

叙事层：从参数到故事

cocktailStoryEngine.ts（16.8KB）负责把参数结果包装为可分享的叙事。配合配方库里每款酒预置的 tagline 与 story 富文本，输出的不只是"喝什么"，而是一个可以被讲述、被拍照、被转发的体验。

这是情绪经济里的关键转化环节：人格标签降低选择成本与社交表达成本，故事卡提供传播载体——但要清醒，它降低的是决策成本，不是替代饮品本身的品质。

6产品矩阵：26 个路由不只是调酒

这个项目的实际规模远超"调酒"二字。

/personality/cocktail/menu/brew/journey /brew/light/brew/music/brew/scent/brew/molecular /prelude/hub/explore/cards /brew/story-preview/tavern/bar-counter/chess /mbti-party/mind/invest/brew/sandbox /brew/balance/poker/login

金色 = 调酒与人格核心链路。/bar-counter（吧台端）与 /menu（酒单）说明产品已经考虑了店员与顾客的双向视角，不是纯 C 端玩具。

几条值得注意的产品线

brew 系列：调制全流程

journey（用户旅程）→ light（灯光）→ music（音乐）→ scent（气味）→ molecular（分子层）→ story-preview（故事预览）。这是一条完整的体验流水线，不是零散页面。

跨场景复用

/poker 德州扑克、/chess 人格棋、/mbti-party 派对、/tavern 酒馆、/invest 投资——同一套向量在不同场景采集与消费，互为数据源。

但这也是风险：26 个路由意味着产品的叙事焦点被稀释。对酒吧客户来说，他不需要知道你有德州扑克和塔罗——他只关心"能不能让客人多点一杯酒"。商业化时必须做减法，把 brew + menu + bar-counter 这条主链路单独拎出来。

10差异化定位：空白不在技术，在闭环

横轴：从内容到交付的完整度；纵轴：从单通道到多感官的统一度。

成熟竞品 Y.Mine 空白区
读图结论：Y.Mine 在纵轴（统一向量编排）上领先所有竞品——这是差异化立足点。但在横轴右侧（线下交付闭环）明显靠后，而那里才是酒吧愿意付钱的地方。

判断：空白是"可复现的感官系统"，不是"人格调酒"

截至 2026 年 9 月，公开资料中尚未发现成熟产品同时满足这六项：

  1. 使用 OCEAN 或可配置六维向量作为统一中间层
  2. 将同一向量确定性派生至酒/色/香/味/音/光
  3. 连接真实酒单、库存、制作规则与安全约束
  4. 保留映射版本、输出日志与设备接口
  5. 面向线下酒吧、品牌活动或硬件生态开放部署
  6. 提供"为何得到这杯酒"的可读解释
必须加上的限定：证据支持的是"成熟组件尚未被公开整合"，不支持"技术方向全球绝对空白"。实验室、品牌定制项目或未公开系统可能已经实现。

因此最稳妥的表述是：「单点人格输入、单通道输出、营销型人格叙事已经红海化；真正可防守的是输入—向量—多输出—制作—反馈的完整闭环。」

优先级路径现实性关键动作收入形式

为什么品牌活动排在酒吧 SaaS 之前：品牌活动能承受一次性高额制作费、周期短、无需立即解决复杂库存与日常运营问题，却能在有限场次内直接验证分享率、加购、客单提升。它是最适合验证"体验溢价是否成立"的入口。
酒吧 SaaS 的铁律：客户持续付费的基础是运营指标，不是"人格报告好看"。首批试点必须追踪并可解释：
  • 互动效果：桌边互动率、测评完成率、分享率
  • 点单转化：从体验到下单的转化率、加购率
  • 商业结果：特调客单价、每桌消费、停留时长
  • 制作交付：调酒师编辑率、制作时长、售罄率
  • 复购传播：回访率、分享后二次访问
若提升主要来自 novelty（新鲜感）而制作成本过高，应优先简化向量维度或收缩配方池。

建议的最小可行试点

目标不是覆盖所有感官，而是在一家真实酒吧跑通闭环。

MVP 范围：30 款门店配方 + 六维向量 + 颜色/音乐/灯光 + 调酒师确认环节，在成都清吧完成 4–8 周试点。对照组：普通菜单 vs 人格体验菜单（按日期或随机分配）。

只有当人格组与非人格组的差异具有可解释性，且调酒师编辑率可控，产品才具备复制条件。

③ OLI 范式 —— 成都验证后，要不要复制到华东华南

OLI（Ownership-Location-Internalization）原用于解释对外直接投资选址。这里借用它判断"跨区域扩张应采取何种组织方式"——自营、授权还是合作。

维度本项目状况推论
O 所有权优势六维向量 → 多感官映射规则是独特资产，可跨门店复现优势存在且可脱离单店存在 → 具备跨区域复制的技术基础
L 区位优势成都（四川 6.0%）门店密度足够验证；但规模化市场在华东 28.6% 与广东 9.1%成都的 L 足以验证产品，不足以支撑规模 → 必须先验证后扩张

OLI 的合成结论：O 有、成都 L 仅够验证、I 在规则层——三者交叉得出唯一路径：在成都自营完成 4–8 周试点（内部化，守住映射规则与数据），验证成功后以"规则内部化 + 地面交付外部化"的方式复制到华东华南。这与第 12 章"成都先行、再复制出去"的建议独立得出、相互印证。

13合规红线：纯前端不等于免责

酒精、数据、算法、生成内容——四条线都要守。

① 酒精业务：年龄门禁 + 审慎传播。《未成年人网络保护条例》2024-01-01 起施行，监管明确面向未成年人的互联网媒介不得发布酒类广告。《广告法》禁止诱导、怂恿饮酒，不得暗示饮酒能消除紧张焦虑或增加体力。产品应：进入酒饮功能前年龄确认、分享卡不美化醉酒/驾驶/过量、显著提示"仅供成年人 · 请理性饮酒"。
② 算法推荐：必须提供非个性化选项。《互联网信息服务算法推荐管理规定》要求显著告知服务情况、说明基本原理与运行机制；用户应能获得非个性化选项、便捷关闭算法推荐、删除用于推荐的特征标签。即使采用纯函数计算，只要形成个性化推荐就应参照执行。
③ 人格数据：属人格推断风险数据。《个人信息保护法》要求敏感信息单独同意；OCEAN 分数虽未必属法定敏感信息，但具人格推断风险。建议：允许游客体验、人格向量与真实身份分离、明确数据控制者与删除路径、不用于歧视性定价或医疗暗示。
④ AI 生成标识：上线前完成，不要事后补救。《人工智能生成合成内容标识办法》2025-09-01 起施行，要求文本/音频/图片/视频/虚拟场景设置显式与隐式标识。当前基于 Web Audio、Canvas 与固定规则的输出，也应标注"算法生成体验方案"，避免用户将娱乐性映射误解为专业心理或风味结论。

14总结与核心价值

这个项目的价值不在"人格调酒"这个概念，而在于把主观体验变成可计算、可复现、可测试的确定性函数。

一句话说清：这个产品是什么

"一个把主观人格翻译成可计算感官参数的多感官体验编排系统。同一组六维向量，确定性地产出酒、色、香、味、音、光——不是六个独立效果，是同一次计算的六个投影。"

差异化：与普通调酒 App 的本质区别

"Cocktail Flow 解决'找配方'，Foodpairing 解决'风味计算'，我解决的是让多个感官通道共享同一套可解释参数。关键差异是可复现——同一输入、同一规则版本，在不同门店应得到一致体验，这是连锁部署的前提。"

边界认知：人格不等于口味

"不能，我也不这么宣称。6×8 矩阵是基于设计判断的权重设定，不是统计结论。我的做法是把它定位为'体验坐标'而非'心理真理'——它降低的是选择成本和社交表达成本，不是替代饮品品质。验证上，下一步是在真实酒吧做 A/B 试点，看转化、客单、制作时长是否改善。"

定位策略：在项目矩阵中的角色

"作为跨域同构的一个落地实例，它展示的是人格向量作为统一数据契约的抽象能力：同一套向量既驱动金融决策链，也驱动多感官体验编排。对金融产品而言它是感官域的旁证，对体验设计而言它是主线产品。"

核心结论

这个项目最值得讲的不是"人格调酒"这个概念，而是三件事：把主观体验抽象成可计算、可测试的确定性函数（6×8 矩阵 + 测试覆盖）；统一数据契约（六通道同源，而非六个独立效果）；清晰的边界认知（不宣称科学效度，清楚合规红线）。

在同类体验类项目中，"知道什么不该做"与"能做出什么"同样稀缺。
